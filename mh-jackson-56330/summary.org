#+begin_src markdown
 Complete Root Cause Analysis

 There are two distinct failures happening, one masking the other. Here's the full chain:

 ### Failure 1: Silent profiler instantiation failure in the forked process

 JMH's architecture splits profiler work between two processes:
 - Runner (parent JVM): ExternalProfiler methods — beforeTrial(), afterTrial(), addJVMOptions(). These print # Preparing profilers: NativeAsyncProfiler.
 - Forked process (native image): InternalProfiler methods — beforeIteration(), afterIteration(). These print [async-profiler] start,... and [async-profiler] stop.

 In the forked native image, BenchmarkHandler calls ProfilerFactory.getSupportedInternal() to create a new instance of the profiler. This goes through getProfilerOrNull():

 ```java
   // ProfilerFactory.java line 50
   private static Profiler getProfilerOrNull(ProfilerConfig cfg) {
       try {
           return getProfiler(cfg);
       } catch (Exception e) {
           return null;  // ← SILENTLY SWALLOWS ALL ERRORS
       }
   }
 ```

 When the constructor throws, the profiler is silently skipped. The internal profilers list ends up empty, so beforeIteration() / afterIteration() are never called, and no [async-profiler] messages appear.

 ### Failure 2: async-profiler's JNI_OnLoad requires JVMTI

 The actual exception thrown inside the forked native image is:

 ```
   java.lang.UnsatisfiedLinkError: Unsupported JNI version 0x0,
       required by /home/agentuser/opt/async-profiler-4.5-linux-x64/lib/libasyncProfiler.so
 ```

 This happens because:

 1. NativeAsyncProfiler(initLine) → super(initLine) → AsyncProfiler constructor → JavaApi.getInstance(libPath) → System.load(libasyncProfiler.so)
 2. Native image calls JNI_OnLoad in the library
 3. async-profiler's JNI_OnLoad calls JavaVM->GetEnv(&env, 0x30010000) requesting JVMTI version 1.0
 4. GraalVM native image doesn't support JVMTI in the way async-profiler needs → GetEnv fails
 5. JNI_OnLoad returns 0 (error)
 6. Native image interprets JNI version 0x0 as unsupported → throws UnsatisfiedLinkError
 7. AsyncProfiler constructor wraps this as ProfilerException
 8. getProfilerOrNull() catches it and returns null

 I confirmed this by disassembling JNI_OnLoad in libasyncProfiler.so:

 ```asm
   # offset 0x505a5: mov $0x30010000,%edx     ← JVMTI_VERSION_1_0
   # offset 0x505b1: call *0x30(%rax)          ← JavaVM->GetEnv()
   # offset 0x505b6: jne 505c6                ← if GetEnv fails, jump to error return
   # offset 0x505c6: xor %eax,%eax            ← return 0 (failure)
 ```

 ### The libPath option

 libPath is a profiler-specific option defined inside AsyncProfiler's constructor via joptsimple:

 ```java
   OptionSpec<String> optLibPath = parser.accepts("libPath",
       "Location of asyncProfiler library. If not specified, System.loadLibrary will be used...")
       .withRequiredArg().ofType(String.class).describedAs("path");
 ```

 It's passed on the command line as part of the -prof flag, with profiler options separated by semicolons:

 ```bash
   # Without libPath (uses System.loadLibrary, needs LD_LIBRARY_PATH):
   -prof org.mendrugo.fibula.NativeAsyncProfiler

   # With libPath (uses System.load with absolute path):
   -prof "org.mendrugo.fibula.NativeAsyncProfiler:libPath=/home/agentuser/opt/async-profiler-4.5-linux-x64/lib/libasyncProfiler.so"

   # Multiple options separated by semicolons:
   -prof "org.mendrugo.fibula.NativeAsyncProfiler:verbose=true;libPath=/home/agentuser/opt/async-profiler-4.5-linux-x64/lib/libasyncProfiler.so"
 ```

 When libPath is set, the constructor calls JavaApi.getInstance(libPathValue) → System.load(libPathValue) (absolute path).
 When libPath is not set, it calls JavaApi.getInstance() → System.loadLibrary("asyncProfiler") (searches java.library.path/LD_LIBRARY_PATH).

 Either way, both paths end up calling JNI_OnLoad, which fails in native image.

 ### The exact JNI registration JSON

 Even though it won't help with the current JVMTI blocker, here's the JNI config that would be needed for RegisterNatives to bind the native methods to AsyncProfiler$JavaApi IF the library could load. async-profiler's JNI_OnLoad uses JVMTI stack walking to find the calling class

 ```json
   {
     "name": "org.openjdk.jmh.profile.AsyncProfiler$JavaApi",
     "methods": [
       {"name": "start0",        "parameterTypes": ["java.lang.String", "long", "boolean"]},
       {"name": "stop0",         "parameterTypes": []},
       {"name": "execute0",      "parameterTypes": ["java.lang.String"]},
       {"name": "getSamples",    "parameterTypes": []},

     ]
   }
 ```

 These entries would go in fibula-core/src/main/resources/META-INF/native-image/org.mendrugo.fibula/fibula-core/jni-config.json.

 The reflection config already exists and is correct — NativeAsyncProfiler and the enum types (OutputType, Direction, CStackMode) are already registered in reflect-config.json.

 ### The path forward

 The System.load()/System.loadLibrary() approach (JNI JavaApi) cannot work in native image because async-profiler's JNI_OnLoad fundamentally requires JVMTI.

 The working alternative is the LD_PRELOAD approach (already sketched in the commented-out code in NativeAsyncProfiler). I confirmed it works:

 ```bash
   $ env LD_PRELOAD=/home/agentuser/opt/async-profiler-4.5-linux-x64/lib/libasyncProfiler.so \
         ASPROF_COMMAND="start,event=cpu,cstack=dwarf,file=profile.html" \
         target/benchmarks 127.0.0.1 12345
   Profiling started
 ```

 With LD_PRELOAD, the library is loaded via the dynamic linker's constructor mechanism (Agent_OnLoad), bypassing JNI_OnLoad and the JVMTI requirement entirely. The ASPROF_COMMAND environment variable tells async-profiler what to do. This would be implemented via
 addJVMInvokeOptions() (as shown in the commented-out code) to prepend env LD_PRELOAD=... ASPROF_COMMAND=... before the forked native image command.

#+begin_src markdown
 No ServiceLoader service file for Profiler. So the profiler discovery falls through to Class.forName(), which fails in native image because NativeAsyncProfiler is not in the reflection configuration.

 Here's the complete analysis:

 ────────────────────────────────────────────────────────────────────────────────

 Root Cause

 The [async-profiler] start,... message never appears because the NativeAsyncProfiler is never instantiated inside the forked native image process. Here's the chain of events:

 ### How JMH profilers work

 JMH's AsyncProfiler implements both ExternalProfiler and InternalProfiler:
 - ExternalProfiler methods (beforeTrial, afterTrial, addJVMOptions) run in the runner/parent JVM process
 - InternalProfiler methods (beforeIteration, afterIteration) run in the forked child process

 The [async-profiler] start,event=cpu message is printed by AsyncProfiler.execute() (called from beforeIteration()), which runs inside the forked process.

 ### What happens in the forked native image

 1. The native image runs NativeForkedMain → ForkedMain.main() → ForkedRunner → BaseRunner.runBenchmark() → BenchmarkHandler.<init>()

 2. BenchmarkHandler constructor calls ProfilerFactory.getSupportedInternal(options.getProfilers()) to create internal profilers inside the forked process.

 3. ProfilerFactory.getProfiler() tries three approaches:
     - Built-in profilers map → not found
     - ServiceLoader<Profiler> discovery → no service file exists in the jar
     - Class.forName("org.mendrugo.fibula.NativeAsyncProfiler") → ClassNotFoundException!

 4. The ClassNotFoundException is silently caught by getProfilerOrNull():
    ```java
      private static Profiler getProfilerOrNull(ProfilerConfig cfg) {
          try {
              return getProfiler(cfg);
          } catch (Exception e) {
              return null;  // silently swallowed!
          }
      }
    ```

 5. Result: the internal profilers list is empty, so beforeIteration() and afterIteration() are never called, async-profiler is never started, and no [async-profiler] messages appear.

 ### Why Class.forName() fails

 In GraalVM native image, Class.forName() only works for classes registered in reflect-config.json. The class org.mendrugo.fibula.NativeAsyncProfiler is not registered in either:
 - fibula-core/src/main/resources/META-INF/native-image/org.mendrugo.fibula/fibula-core/reflect-config.json
 - 2609-handles/target/classes/META-INF/native-image/reflect-config.json

 ### Evidence

 Adding a debug print to getProfilerOrNull() reveals:

 ```
   [DEBUG] Failed to create profiler: org.mendrugo.fibula.NativeAsyncProfiler, error: java.lang.ClassNotFoundException: org.mendrugo.fibula.NativeAsyncProfiler
       at org.graalvm.nativeimage.builder/com.oracle.svm.core.hub.registry.ClassRegistries.forName(ClassRegistries.java:243)
       at java.base@25.0.4.1/java.lang.Class.forName0(DynamicHub.java:2036)
       at java.base@25.0.4.1/java.lang.Class.forName(DynamicHub.java:467)
       at org.openjdk.jmh.profile.ProfilerFactory.getProfiler(ProfilerFactory.java:78)
       ...
 ```

 How to Fix

 To make NativeAsyncProfiler work, at minimum:

 1. Register NativeAsyncProfiler for reflection in the native image config so Class.forName() and reflective constructor invocation work. Add to reflect-config.json:
    ```json
      {
        "name": "org.mendrugo.fibula.NativeAsyncProfiler",
        "methods": [
          {"name": "<init>", "parameterTypes": ["java.lang.String"]},
          {"name": "<init>", "parameterTypes": []}
        ]
      }
    ```

 2. Register AsyncProfiler$JavaApi JNI native methods in jni-config.json so that System.load()/System.loadLibrary() can bind the native methods (execute0, start0, stop0, getSamples, filterThread0).

 3. Ensure the async-profiler library path is passed correctly (via libPath option) since java.library.path may differ in native image.

 How I Debugged This (and how GDB could be used)

 I added a print statement to ProfilerFactory.getProfilerOrNull() in JMH to print the exception instead of silently returning null, rebuilt JMH (mvn install -DskipTests -pl jmh-core), rebuilt fibula-core, rebuilt the benchmark (mvn clean package), and re-ran. The
 ClassNotFoundException stack trace immediately revealed the issue.

 Using GDB would also be possible after rebuilding with debug info (mvn clean package -Ddebug=true -DbuildArgs=-H:+SourceLevelDebug,-H:+TrackNodeSourcePosition,-H:+DebugCodeInfoUseSourceMappings):

 1. The forked command shown in the output already includes -agentlib:jdwp=transport=dt_socket,server=y,suspend=y,address=*:5005 which is a JDWP debugger argument (not GDB), but this won't work for a native image binary since JDWP is a JVM feature.

 2. For GDB with native image, you would:
     - Run the benchmark runner: java -jar target/benchmarks.jar -prof "org.mendrugo.fibula.NativeAsyncProfiler:..." ...
     - When the native image fork starts, note its PID
     - Attach GDB: gdb -p <pid> or modify the fork command to use GDB: wrap the forked binary invocation
     - With the debug symbols (-H:+SourceLevelDebug), you can set breakpoints on Java methods like break 'org.openjdk.jmh.profile.ProfilerFactory::getProfilerOrNull' and inspect the exception
     - Alternatively, since suspend=y is in the fork command args (and native image ignores it), you could override addJVMOptions in NativeAsyncProfiler to instead add a sleep/wait mechanism that gives time to attach GDB

#+begin_src markdown
 This confirms it perfectly. The .eh_frame in the main binary covers only C library functions (starting at 0x901b40+) and a few entry points. The .debug_frame in benchmarks.debug covers the actual Java AOT-compiled code (starting at 0x020000, which is the start of .text where

 Here's the complete analysis:

 ────────────────────────────────────────────────────────────────────────────────

 Root Cause

 The issue is in async-profiler v4.5's symbol/DWARF loading logic and how it interacts with GraalVM native image's split debug info.

 ### The Two DWARF Sources

 GraalVM's native image build with -Ddebug=true produces:
 - benchmarks (main binary): contains .eh_frame/.eh_frame_hdr with only 655 FDEs — these cover the C runtime/entry point functions, NOT the AOT-compiled Java methods
 - benchmarks.debug (separate debug info, linked via .gnu_debuglink): contains .debug_frame with 15,717 FDEs — these cover ALL AOT-compiled Java methods

 ### async-profiler's Loading Logic (v4.5)

 In symbols_linux.cpp, ElfParser::loadSymbols():

 ```cpp
   ElfSection* symtab = findSection(SHT_SYMTAB, ".symtab");
   if (symtab != NULL) {
       loadSymbolTable(...);           // loads symbols
       _cc->setDebugSymbols(true);     // marks debug symbols as found
   } else if (use_debug) {
       // Follow .gnu_debuglink to external debug file
       loadSymbolsUsingBuildId() || loadSymbolsUsingDebugLink();
   }
 ```

 When -H:-DeleteLocalSymbols keeps local symbols (BAD case):
 1. .symtab IS found in the main binary → symbols loaded → setDebugSymbols(true)
 2. The else if branch is skipped → benchmarks.debug is never opened
 3. .debug_frame (15,717 FDEs) is never parsed
 4. Later, parseProgramHeaders() → parseUnwindInfo() parses .eh_frame_hdr → only 655 FDEs
 5. DWARF unwinding fails for all AOT-compiled Java methods → flat stack traces

 When local symbols are deleted (GOOD case):
 1. No .symtab in main binary → falls through to loadSymbolsUsingDebugLink()
 2. Opens benchmarks.debug → parseFile(cc, base, path, use_debug=false)
 3. Since use_debug=false, parseDebugFrameSection() IS called
 4. .debug_frame (15,717 FDEs) is parsed → complete DWARF table set
 5. Later, parseUnwindInfo() sees hasDwarfTable() returns true → skips .eh_frame_hdr
 6. DWARF unwinding works for all methods → correct flame graph

 ### The Bug

 The presence of .symtab (local symbols) in the main binary prevents async-profiler from following .gnu_debuglink to the separate debug file. This is a problem because:
 - .symtab and .debug_frame serve different purposes (symbol names vs. stack unwinding)
 - Finding symbol names should not prevent loading DWARF frame descriptors from the debug file
 - The main binary's .eh_frame is incomplete for GraalVM native images (only covers C runtime, not Java AOT code)

 The fix in async-profiler would be to decouple the debug symbol loading from the DWARF frame loading — even when .symtab is found in the main binary, it should still check the external debug file for .debug_frame if the .eh_frame coverage is insufficient, or always follow
 .gnu_debuglink for .debug_frame regardless of whether .symtab was found.
